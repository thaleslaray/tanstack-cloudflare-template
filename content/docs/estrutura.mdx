Saber onde cada coisa fica economiza muito tempo. Este é o mapa do projeto, na ordem em que você provavelmente vai precisar dele.

## As pastas principais

| Caminho | O que tem lá |
| --- | --- |
| `src/routes` | As páginas. Cada arquivo vira uma URL (`blog/index.tsx` vira `/blog`). |
| `src/routes/api` | Endpoints de API, como o do login (`api/auth/$.ts`). |
| `src/db` | O schema do banco (Drizzle) e a função que abre o D1. |
| `src/lib` | Código de apoio: autenticação, e-mail, conteúdo MDX, utilitários. |
| `src/content` | Os textos da landing, como dados. |
| `content/` | Os artigos em MDX: blog, docs, termos e privacidade. |
| `src/components` | Peças de interface, incluindo o `ui/` do shadcn. |
| `wrangler.jsonc` | A configuração do Worker e dos bindings. |
| `worker-configuration.d.ts` | Os tipos do `env`, gerados a partir do `wrangler.jsonc`. Não edite à mão. |
| `drizzle/` | As migrations geradas. |

Repare que existem duas pastas parecidas: `src/content` guarda os dados da landing, e `content/` (na raiz) guarda os arquivos `.mdx`.

## Trocar a landing

A página inicial não tem texto escrito dentro dela. Ela lê uma lista de blocos em `src/content/landing.ts` e desenha cada um. Para mudar o título, os botões ou as seções, edite essa lista. Para mudar o nome do app, o e-mail de suporte ou a descrição, edite `src/config/app.ts`.

## Blocos da landing

Cada item da lista em `src/content/landing.ts` é um bloco, e o campo `type` diz o formato. São 13:

| `type` | O que desenha |
| --- | --- |
| `hero` | A primeira tela: promessa, uma linha de apoio e dois botões. |
| `stats` | Uma faixa de números grandes com rótulo. |
| `stack` | Uma fileira de nomes em pílulas, logo abaixo do hero. |
| `logos` | Nomes de clientes ou tecnologias, em texto com SVG opcional; pode ser agrupada. |
| `features` | Cartões iguais, três por linha. |
| `bento` | Cartões de tamanhos diferentes numa grade; o largo ou destacado puxa o olho. |
| `compare` | Duas colunas, "antes / depois" ou "eles / nós". |
| `steps` | Passos numerados, cada um com um bloco de comandos. |
| `terminal` | Uma janela de terminal com os comandos sendo digitados. |
| `gallery` | Imagens da pasta `public/` com legenda. |
| `testimonials` | Depoimentos em cartões. |
| `faq` | Perguntas que abrem e fecham. |
| `cta` | A última frase da página e o botão. |

Para ver um exemplo de cada um, rode `npm run dev` e abra [/blocos](/blocos). Os dados de lá estão em `src/content/blocos-exemplo.ts`: copie o objeto do bloco que quiser para `landing.ts` e troque o texto. Os campos de cada formato estão comentados em `src/components/landing/types.ts`.

Precisa de um formato que não existe? São três passos: o tipo em `types.ts`, um componente em `src/components/landing/blocks/` e um `case` em `render.tsx`. O typecheck avisa se faltar o `case`, e o teste `render.test.tsx` avisa se faltar o exemplo.

## Criar uma tela

As telas da área logada são montadas com peças prontas, que ficam em `src/components/app/` e `src/components/ui/`: cabeçalho da página, faixa de busca, tabela, lista vazia, campo de formulário, bolinha de estado, diálogo. Para ver todas no tema atual, rode `npm run dev` e abra [/estilo](/estilo). Lá também está a tela de lista de referência, funcionando: filtre, busque, crie um item.

Uma tela nova é um arquivo em `src/routes/_app/app/` e uma linha em `mainNav` (`src/components/app-sidebar.tsx`), para ela aparecer no menu. Com o Claude Code, peça `/tela` e diga o que quer ("cria uma tela de clientes"): a skill escolhe as peças, liga os dados e confere o resultado no celular e no modo escuro.

As regras de aparência (cor só por token, um botão da marca por tela, nada de sombra) estão em `src/CLAUDE.md`, e várias são conferidas pelo `npm run test`.

## Escrever artigos

Para criar um post, adicione um arquivo em `content/blog/` com o frontmatter `title`, `description` e `date`. Para uma página de documentação, use `content/docs/` com `order`. O nome do arquivo vira o endereço: `content/blog/meu-post.mdx` vira `/blog/meu-post`. Se o frontmatter estiver errado, o build avisa na hora.

## Criar uma tabela

1. Declare a tabela em `src/db/schema.ts`.
2. Gere a migration com `npm run db:generate`.
3. Aplique no banco local com `npm run db:migrate:local`.

Quando for publicar, `npm run deploy` aplica as migrações no banco remoto antes de subir o código (ou, à mão, `npm run db:migrate:remote`). O arquivo `src/db/auth-schema.ts` espelha as tabelas do login; mexa nele só se mudar os plugins do Better Auth.

## Como funcionam os bindings

Um **binding** é uma ligação entre o seu código e um recurso da Cloudflare: o banco D1, o bucket R2, um Durable Object, um segredo. Você declara todos no `wrangler.jsonc` (D1 em `d1_databases`, R2 em `r2_buckets`, e assim por diante) e usa assim:

```ts
import { env } from 'cloudflare:workers'

const db = getDb(env.DB)
```

Três regras evitam dor de cabeça:

- Use `env` **só dentro** de uma server function ou de um handler, nunca no topo do arquivo.
- Nunca importe `env` em código que roda no navegador.
- Depois de mudar o `wrangler.jsonc`, rode `npm run cf-typegen` para regenerar os tipos em `worker-configuration.d.ts`. Segredos não ficam no `wrangler.jsonc`: a lista deles é o `.dev.vars.example`.

## Páginas públicas e páginas com sessão

As páginas de conteúdo (landing, blog, docs, termos e privacidade) são pré-renderizadas no build: viram HTML estático. Páginas que dependem de sessão ou de bindings, como `/login`, `/app` (a área logada), `/demo` (que só existe no `npm run dev`) e `/api`, **nunca** são pré-renderizadas. A lista do que pode ser estático está em `src/config/public-paths.ts`.
