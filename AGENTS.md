# tanstack-cloudflare-template

Template de app full-stack rodando 100% em um Cloudflare Worker, com o
`@cloudflare/vite-plugin` v1 e o Wrangler (o caminho estável do guia oficial).
Público: quem está aprendendo. Explique o que
fizer em pt-BR, simples e direto.

## Stack
TanStack Start (React 19) + Router + Query, Tailwind v4 + shadcn/ui, Drizzle
sobre D1, Better Auth (código por e-mail, Google/GitHub opcionais, senha
opcional), R2, Durable Object `Counter`, cron, MDX (blog/docs/legal) com
prerender, rate limit, cabeçalhos de segurança, Biome, Vitest, Playwright.
Entry do Worker em `src/server.ts`; config em `wrangler.jsonc`.

## Comandos
- `npm run dev` — `vite dev --port 3000` em http://localhost:3000 (outra porta: `npx vite dev --port 3001`; a URL vem da requisição, então `BETTER_AUTH_URL` só importa se o `.dev.vars` o tiver preenchido: nesse caso, ajuste a porta nele)
- `npm run build` — `vite build` (saída em `dist/client` e `dist/server`, com prerender); antes, o `prebuild` roda `npm run sitemap`
- `npm run sitemap` — `scripts/generate-sitemap.ts` (via `tsx`) reescreve `public/sitemap.xml` e `public/robots.txt` a partir de `src/config/app.ts`, `src/config/public-paths.ts` e `content/`
- `npm run preview` — build + `vite preview` (a saída de produção, local)
- `npm run cf-typegen` — `wrangler types --env-file .dev.vars.example` → `worker-configuration.d.ts`
- `npm run typecheck` — `cf-typegen` + `tsc --noEmit`
- `npm run check` / `check:fix` — Biome
- `npm run test` — Vitest (unidades, ambiente node, `cloudflare:workers` substituído por `src/test/cloudflare-workers.ts`)
- `npm run e2e` — Playwright (5 specs, 27 testes); sobe o `vite dev` sozinho e grava o log em `e2e/.dev.log` (é de lá que o teste de login lê o código), e também o `npm run preview` na porta 4173 (`E2E_PREVIEW_PORT`), para checar os cabeçalhos do `public/_headers` nos estáticos. Porta ocupada: `E2E_PORT=3001 npm run e2e` (a URL vem da requisição; só ajuste `BETTER_AUTH_URL` no `.dev.vars` se ele estiver preenchido)
- `npm run load` / `npm run load:sessoes` — teste de carga com k6 (não precisa instalar: `scripts/k6.mjs` baixa a versão fixa do site oficial, confere a SHA-256 e guarda em `node_modules/.cache/k6/`; usa `K6_BIN` ou o `k6` do PATH se houver; `npm run k6 -- <comando>` roda outro comando; veja `load/README.md`); gasta cota e cria dados na conta, só com o ok do usuário. As rotas medidas e a escrita ficam em `load/rotas.json` (o padrão é a tela de clientes de exemplo): ajuste às telas do produto antes de rodar; rota que responde 404 faz o roteiro parar. **Deixe a escrita LIGADA** (não `null`) com campos que passem na validação do produto (o servidor responde 200 mesmo ao recusar; o `setup` grava um registro de teste antes de medir e para com a mensagem do servidor; `{n}` vira `<VU>-<rodada>`, com hífen, e `{num}` vira 6 dígitos para campo só de dígitos, ex.: telefone `"11987{num}"`). No build de produção o roteiro acha os ids das server functions calculando `sha256("<arquivo>--<função>_createServerFn_handler")` e conferindo nos JS servidos (`load/ids.js`)
- `npm run test:cold` — `scripts/cold-start-check.ts`: sobe um `vite dev` próprio na porta 3907 (`COLD_PORT`), abandona o primeiro pedido de quatro páginas e confere que todas continuam respondendo (uns 15 s). Roda no CI.
- `npm run db:generate` — migração a partir de `src/db/schema.ts` e `src/db/auth-schema.ts`
- `npm run db:migrate:local` / `db:migrate:remote`
- `npx wrangler deploy --dry-run` (depois de `npm run build`) — valida sem publicar; `npm run deploy -- --secrets-file .prod.vars` publica (o `predeploy` aplica as migrações remotas antes)
- Cron local: `curl "http://localhost:3000/cdn-cgi/local/scheduled?cron=0+3+*+*+*"`
- Local Explorer (D1, R2, DO, logs): http://localhost:3000/cdn-cgi/local/explorer
- Skills: `/setup`, `/deploy`, `/google-oauth`, `/tela` (em `.claude/skills/`). Pedido de tela nova ou de "deixar bonito"? Siga a `/tela`.
- CI (GitHub Actions, sem deploy): `.github/workflows/ci.yml` em push na `main` e PR (`npm ci`, `.dev.vars` com segredo aleatório, typecheck, check, test, `test:cold`, build, `wrangler deploy --dry-run`, e falha se `npm run db:generate` mudar `drizzle/`); `e2e.yml` à mão e toda segunda 09:00 UTC.

### Antes de dizer que terminou
Rode `npm run check:fix`, `npm run typecheck` e `npm run test` e leia a saída. Rota nova: deixe o `npm run dev` rodando (o plugin regera o `routeTree.gen.ts`) ou rode `npm run build`. Mexeu em tela: abra no navegador e olhe (celular, escuro). Mexeu em auth, guard ou cabeçalhos: `npm run e2e`. Diga o que conferiu e o que não conferiu; "deve funcionar" não é conferido.

## Regras

### O que sempre precisa de um "sim" de quem pediu
Pergunte e espere a confirmação antes de: publicar (`npm run deploy`, `wrangler deploy`, `versions deploy`, `rollback`); qualquer comando com `--remote` (migração ou `d1 execute` no banco de produção); `wrangler secret put/delete/bulk`; apagar banco, bucket ou Worker na Cloudflare; `npm run load` (gasta a cota e cria dados na conta real); `git push` (e nunca `--force`); `git reset --hard`, `git clean`, `git checkout -- .`; apagar `.dev.vars`, `.prod.vars` ou `.wrangler/state/` (é o banco local; numa worktree descartável de ticket, cujo banco local só tem dados de teste, apagar ou recriar o `.wrangler/state` não pede "sim"). Motivo: são ações na conta ou nos dados da pessoa e não têm desfazer. `npx wrangler deploy --dry-run` não publica e pode rodar à vontade.

As regras marcadas com (teste) são verificadas por `src/rules.test.ts` (roda no `npm run test`).

- (teste) A config é `wrangler.jsonc` (com `$schema`; nomes de campo conferidos em `node_modules/wrangler/config-schema.json`). NÃO instalar o `cf` nem criar `cloudflare.config.ts` até o GA do `cf`/plugin v2: o `cf` ignora o `wrangler.jsonc` e pode gerar config sem bindings; o Wrangler não publica saída do v2. O caminho de ida, no GA, é `npx cf migrate` (o estado v2 está guardado na branch `cf-v2-beta`).
- Dependências com `^` (minor e patch sobem sozinhos) e `package-lock.json` versionado: quem clona recebe o que está no lock. Com o botão Deploy (Workers Builds), mesclar PR do Dependabot na `main` publica o app. O Dependabot (`.github/dependabot.yml`) abre PRs semanais agrupados e o CI valida cada um. Pin exato (sem `^`) só para pacote em beta, com o motivo escrito aqui; hoje não há nenhum.
- **Prazo para dependência vulnerável** (aviso do `npm audit`, do Dependabot ou do CI) que o app alcança em produção: severidade alta ou crítica, corrigir em até 7 dias; média, em até 30; baixa, no próximo ciclo normal. Vulnerabilidade só de ferramenta de desenvolvimento (build, teste) entra no mesmo prazo, mas pode esperar o Dependabot se não for alcançável em produção. Não dá para corrigir no prazo? Registre aqui a exceção, com o motivo e a data.
- **CI**: as actions do `.github/workflows/` ficam fixadas por SHA (comentário com a versão ao lado; o Dependabot, `github-actions`, abre o PR para subir). O job `segredos` roda o gitleaks (action oficial) no histórico inteiro a cada push/PR.
- `compatibility_date` no `wrangler.jsonc` não é dependência: é o contrato com o runtime. Sobe à mão, lendo o changelog, e com `typecheck`, `build`, `test` e `e2e` verdes.
- Tipos de `Env` ficam em `worker-configuration.d.ts`, gerados por `npm run cf-typegen` a partir do `wrangler.jsonc` + chaves do `.dev.vars.example` (o `--env-file` faz funcionar em clone limpo, sem `.dev.vars`). Mudou `wrangler.jsonc` ou o `.dev.vars.example`? Regenere e versione o arquivo.
- No `vite.config.ts`: `devtools()` primeiro, depois MDX (`enforce: 'pre'`) e `mdxMeta()`, depois `cloudflare({ viteEnvironment: { name: 'ssr' } })` ANTES de `tanstackStart()`. Não reordenar.
- (teste) Bindings só via `import { env } from "cloudflare:workers"` em código de servidor (server functions, handlers, `src/lib/*` de servidor); ler `env` dentro de função, nunca em escopo de módulo, nunca em código que vá ao client. Sem `process.env` em `src/`.
- `getAuth(env, request)` e `getDb(env.DB)` são factories por request. Sem singletons. Passe a `request` sempre que tiver uma (handler, `getRequest()`): sem `BETTER_AUTH_URL`, a URL do app vem da origem dela; o Better Auth só deduz sozinho dentro do `handler`, não em `api.getSession`. `tanstackStartCookies()` é sempre o último plugin do Better Auth.
- (teste) **React.lazy só no cliente.** Componente criado com `lazy(() => import(...))` é renderizado dentro de `<ClientOnly>` (de `@tanstack/react-router`), como o `Toaster` e o `Devtools` em `src/routes/__root.tsx`. Motivo: no workerd o `import()` pertence ao pedido que o disparou; com o `lazy` no escopo do módulo, se o primeiro pedido termina antes de o módulo carregar (um `HEAD /`, uma aba fechada), a promessa fica presa ao pedido morto e nenhuma página responde mais até reiniciar o servidor (no log, 2 min depois: `SSR stream transform exceeded maximum lifetime`). O mesmo vale para qualquer promessa guardada em variável de módulo e esperada por outro pedido: não faça. `src/rules.test.ts` confere pelo texto e `npm run test:cold` confere no servidor de verdade.
- D1 é SQLite: sem transação aninhada; use `db.batch([...])` ou uma instrução condicional.
- Aguardar (`await`) toda promise; no `scheduled`, `ctx.waitUntil`.
- Sem `eval`/MDX em runtime e sem filesystem real no Worker.

### Antes de mexer na plataforma (Cloudflare)
- Vai mexer em `wrangler.jsonc`, criar ou trocar um binding, ou usar D1, R2, Durable Object, fila, cron, Email Service, rate limit ou deploy de um jeito que este arquivo ainda não descreve? Consulte a fonte ANTES de escrever. A Cloudflare muda rápido e o que o modelo lembra costuma estar velho (nome de campo, limite, preço, forma da API).
- Ordem: a skill `cloudflare-atlas`, se estiver instalada; senão as do plugin oficial da Cloudflare (`cloudflare` para escolher e ligar produtos, `workers-best-practices` para código de Worker, `wrangler` para a config e os comandos, `durable-objects`, `cloudflare-email-service`); sem nenhuma, a página da doc em Markdown: `curl -sL -H "Accept: text/markdown" https://developers.cloudflare.com/<caminho>/`.
- O que as skills NÃO decidem são as regras deste projeto (as seções abaixo). Se a skill e este arquivo divergirem sobre como ESTE app faz algo, vale este arquivo; se divergirem sobre como a plataforma funciona, vale a fonte mais nova, e este arquivo deve ser corrigido.
- Não precisa consultar para o que não toca a plataforma: tela, texto, estilo, rota, teste. Para isso valem o `DESIGN.md`, o `src/CLAUDE.md` e a skill `/tela`.

### Segredos e URL
- Locais em `.dev.vars` (não versionado); a lista de chaves é `.dev.vars.example`, que também alimenta os tipos. Novo segredo? Adicione nos dois e rode `npm run cf-typegen`. Segredo nunca vai em `"vars"`.
- Não usamos `"secrets": { "required": [...] }` no `wrangler.jsonc` de propósito: com ele o `wrangler deploy` exige TODOS os listados, e os opcionais (`RESEND_API_KEY`, `EMAIL_FROM`, `GOOGLE_*`, `GITHUB_*`) bloqueariam o deploy. O código trata string vazia como ausente.
- `BETTER_AUTH_URL`: em dev é OPCIONAL (a URL é deduzida da requisição; crie no `.dev.vars` para fixar uma URL, útil para outra porta). Em PRODUÇÃO é OBRIGATÓRIO como segredo, antes do primeiro deploy (a skill `/deploy` exige): fora do localhost, com a variável definida, o `getAuth` usa `trustedOrigins: [origem dela]` (`resolveTrustedOrigins`, `src/lib/auth-config.ts`); sem ela, cada host que chega ao Worker (workers.dev, domínio próprio) viraria origem confiável, os cookies se separariam por host e o OAuth só funcionaria em um. Não há bloco `"vars"` no `wrangler.jsonc`.
- `appConfig.url` (`src/config/app.ts`) alimenta sitemap, canonical e `og:url`: troque ANTES do build. Com `localhost`, `npm run sitemap` avisa.
- O botão Deploy lê os segredos do `.dev.vars.example` e as descrições do campo `cloudflare.bindings` do `package.json`: segredo novo entra nos dois.
- Produção: `npm run deploy -- --secrets-file .prod.vars` (gitignorado) ou `npx wrangler secret bulk .prod.vars`.

### E-mail
- (teste) Tudo passa por `sendEmail()` em `src/lib/email.ts`. Ordem: Resend (se `RESEND_API_KEY`), binding `EMAIL` do Cloudflare Email Service (`send_email` descomentado no `wrangler.jsonc` e `EMAIL_FROM` definido), senão o e-mail inteiro vai para o console do `npm run dev`. Templates em `src/lib/email-templates.ts`, HTML com estilos inline.

### Auth
- Rate limit em todo POST de `/api/auth/*`, exceto sign-out e get-session, por IP (/64 no IPv6). Por e-mail também, mas só onde há envio de código ou teste de senha (`send-verification-otp`, `sign-in/email`, `sign-up/email`); a VERIFICAÇÃO do código (`sign-in/email-otp`, `email-otp/verify-email`, `check-verification-otp`) fica só com a chave por IP, senão quem soubesse o e-mail de alguém o travaria fora do login (o código tem 3 tentativas, `allowedAttempts`).
- Login com senha vem DESLIGADO (`PASSWORD_LOGIN_ENABLED`); quando ligado, exige verificação de e-mail.
- Com a senha ligada, `hooks.before` recusa senha da lista das mais comuns (`src/lib/password-policy.ts`, código `PASSWORD_TOO_COMMON`). Escolha: lista LOCAL, não o plugin `haveIBeenPwned` (que existe no Better Auth instalado, mas chama `api.pwnedpasswords.com` a cada cadastro: rede de terceiros no login, e cadastro com 500 se ela cair). Mais cobertura = aumentar a lista.
- `/update-user` passa por `databaseHooks.user.update.before` (`sanitizeProfileUpdate`, `src/lib/profile.ts`): `image` só vale se for nulo ou `/api/avatar/<id>[?v=n]` (senão é descartado) e `name` é cortado em `NAME_MAX_LENGTH` (100, o mesmo `maxLength` do campo em `/app/configuracoes`).
- Teste com o Better Auth de verdade: `src/test/auth-harness.ts` (D1 local em memória via `getPlatformProxy`, migrações de `drizzle/` aplicadas); exemplo em `src/lib/auth-integration.test.ts`.
- `getAuth` lança erro se `BETTER_AUTH_SECRET` faltar ou tiver menos de 32 caracteres.
- `sendEmail` lança erro quando não há provedor de e-mail e não é dev (o login recusa enviar, em vez de só logar o código). "Dev" exige `import.meta.env.DEV` (o `vite dev`) E, se `BETTER_AUTH_URL` estiver definido, que seja localhost: um build de produção nunca imprime código no log, nem com a URL de localhost esquecida.
- **Pedido que manda e-mail sem provedor configurado falha na cara.** O Better Auth envia em segundo plano, então um erro de envio só aparecia no log e a tela dizia "enviado". O `hooks.before` chama `assertEmailConfigured(path, passwordEnabled)` (`src/lib/auth-otp.ts`): sem provedor (`hasEmailProvider`, `src/lib/email.ts`) e fora do dev local, responde 503 com `code: 'EMAIL_NAO_CONFIGURADO'` em `POST /api/auth/email-otp/send-verification-otp` (login por código e reenvio da verificação, `type: 'email-verification'`) e em `POST /api/auth/sign-up/email` (só com `PASSWORD_LOGIN_ENABLED` ligado; a conta nem é criada). Vale para qualquer e-mail, tenha conta ou não, para não vazar quem tem. Não cobertos de propósito: `/send-verification-email` e a redefinição de senha (`/request-password-reset`, `/reset-password`) estão em `DISABLED_PATHS` (404); `/sign-in/email` não é bloqueado, pois quem já verificou o e-mail entra normalmente (só o reenvio automático para conta não verificada pode falhar no log). Quem ligar um desses caminhos deve incluí-lo em `EMAIL_SENDING_PATHS`. `auth-failure.ts` traduz para "O envio de e-mail deste sistema ainda não foi configurado. Avise quem administra." Teste: `src/lib/auth-integration.test.ts`.
- Demos (`/demo/*`) só existem no `npm run dev`.
- Encerrar conta exige e-mail verificado e sessão com menos de 1 h.
- Job `auditoria.retencao` apaga a auditoria com mais de 180 dias.
- Respostas de `/app*` levam `Cache-Control: no-store`.
- **Cache da sessão em cookie** (`session.cookieCache`, 60 s, `strategy: 'compact'`, cookie `better-auth.session_data`): o `getSession` não vai ao D1 a cada página. Trade-off: revogar sessão ou encerrar conta só vale nos OUTROS aparelhos depois de até 60 s. Ação sensível lê o banco: `getSession({ headers, query: { disableCookieCache: true } })` (hoje em `requireSession` de `account-fns.ts` e em `api/avatar.ts`; ação sensível nova faz igual). Quem muda dados da sessão (ex.: `user.image`) direto no banco, sem passar pelo Better Auth, precisa devolver o cookie novo: `api/avatar.ts` relê com `disableCookieCache` + `returnHeaders` e copia os `Set-Cookie` (sem isso a foto velha ficava até 60 s). O guard `ACCOUNT_CLOSED` continua barrando login novo. Sem `refreshCache` (é para quem não tem banco).
- Login principal é o plugin `emailOTP` (6 dígitos, `storeOTP: { hash }` com HMAC-SHA-256 e o `BETTER_AUTH_SECRET` como chave (`otpHasher`, `src/lib/auth-config.ts`; o `'hashed'` nativo é SHA-256 puro e cai por força bruta em 6 dígitos), 3 tentativas, 10 min). Sem provedor de e-mail, no `vite dev` o código sai no log (fora dele, o envio falha): `[auth] código de login para <email>: <código>` (o e2e depende dessa linha; não mude o formato).
- **Cadastro só para e-mails liberados** (interruptor `appConfig.accessMode` em `src/config/app.ts`: `'open'` é o padrão, qualquer e-mail entra; `'allowlist'` só a lista; o ticket 01 do produto escolhe). ### D1 e UUID
- **Todo erro do servidor deixa uma linha no log (`src/start.ts`, `src/lib/log-erro.ts`).** Um erro lançado numa server function ou no `loader` vira só um HTTP 500: o TanStack não escreve nada. O middleware global registra `[erro] server function: <mensagem>`, o Worker registra `[500] <método> <caminho>` e `limitarUsuario` registra `[rate-limit] usuário ... passou do limite`. **O limite por usuário (`USER_RATE_LIMIT`, 60 leituras por minuto) estourado numa página dá 500**, não 429: foi a causa provável do 1% de 500 sem log na medição de 17/11/2026 (reproduzido no `vite dev` com 64 GET /app da mesma conta). No k6, use 40 contas ou mais no degrau de 50 req/s (`load/README.md`).
- **Onde o Worker roda importa muito (Placement): com o banco longe do público, fixe a região perto do D1.** O D1 tem um primário numa região só; Worker longe dele paga uma viagem de rede por consulta em fila (130 a 190 ms cada, do Rio ao ENAM). O `wrangler.jsonc` vem com `"placement": { "mode": "smart" }` (colocação automática), que só move o Worker se ele já rodou perto do banco. Com público só no Brasil ele fica no Rio: `cf-placement: local-GIG` por 56 min com o D1 em ENAM. A dica explícita é `"placement": { "region": "aws:us-east-1" }` (formato `provedor:região`, `aws`/`gcp`/`azure`; as estratégias `mode`, `region`, `host` e `hostname` se excluem; `src/placement.test.ts` confere). O padrão fica `smart` porque cada projeto tem o banco numa região diferente. **Medido em 18/11/2026** (Worker de teste, D1 em ENAM, k6 vindo do Brasil, `cf-placement: remote-IAD` confirmado), p95 de região fixa contra automática: estático 22 / 28 ms, login 198 / 103, logado 248 / 378, gravação 278 / 507; 0% de falhas nas duas. Dentro do Worker, GET /app: 19 ms contra 246 ms. Só a página pública renderizada no servidor piorou (103 para 198 ms), as duas dentro da meta de 300 ms. O D1 não tem região na América do Sul. **Antes de medir, confira `cf-placement` (deve mostrar `remote-<local perto do banco>`) e espere a colocação ficar ativa:** a medição de 17/11 foi feita antes disso e deu login 708 ms e logado 741 ms, números errados. Pré-renderizadas e `/assets/` saem sempre do ponto mais perto do visitante. Como decidir: com `PERF_LOG=1`, compare `colo` (onde o Worker rodou) com `d1[].r` (de onde o D1 respondeu, ex.: `ENAM`) e olhe `fila`. Passo a passo e comandos: skill `/deploy` ("Onde o Worker roda").
- **Onde fica o banco**: sem `database_id`, o D1 é criado pelo provisionamento automático do primeiro deploy, no lugar "perto de quem pediu a criação" (doc "Data location"), e **não muda depois**. Para escolher: `npx wrangler d1 create <nome> --location=<dica>` (`wnam`, `enam`, `weur`, `eeur`, `apac`, `oc`; não existe dica para América do Sul, África nem Oriente Médio, o D1 não roda lá; para o Brasil use `enam`) e acrescente o `database_id` ao `wrangler.jsonc`; a dica é "o mais perto possível", não garantia. `--jurisdiction=eu|us|fedramp` restringe onde o banco roda e guarda dados (conformidade), e vale mais que a dica. Nunca rode isso sem o "sim" de quem pediu.
- **`getDb` usa a sessão D1 do pedido** (Sessions API). `src/server.ts` cria `env.DB.withSession(bookmark ?? 'first-unconstrained')` por pedido e roda o handler dentro de um `AsyncLocalStorage` (`src/db/d1-session.ts`); `getDb(env.DB)` pega essa sessão, e sem pedido (cron/scheduled, testes) usa o D1 direto, no primário. Depois da resposta, o bookmark vai no cookie `d1-bookmark` (HttpOnly, SameSite=Lax, 1 h; fora do localhost com `Secure` e o nome `__Host-d1-bookmark`, e a leitura aceita os dois nomes durante a transição), e o pedido seguinte parte dele: quem acabou de escrever lê a própria escrita. O cookie vem do cliente, então só vale se bater com o formato (`isValidBookmark`). NUNCA guarde a sessão em variável de módulo.
- **Réplica de leitura (D1 Read Replication) é um passo manual de conta**, fora do código: painel da Cloudflare, D1, o banco, **Settings > Enable Read Replication** (ou a API `PUT .../d1/database/<id>` com `{"read_replication":{"mode":"auto"}}`; o Wrangler não tem comando para isso). O código já está pronto (a Sessions API acima); sem ligar nada quebra: `withSession` sem réplica manda tudo ao primário. Prós: leitura serve da réplica mais perto de quem pede, sem custo extra de armazenamento ou computação (cobra-se o mesmo `rows_read`/`rows_written`); mais vazão de leitura. Contras e limites: as escritas sempre vão ao primário; a réplica pode estar atrasada (a Sessions API + o cookie `d1-bookmark` dão consistência sequencial: quem escreveu lê a própria escrita); **as réplicas ficam em ENAM, WNAM, WEUR, EEUR, APAC e OC, não existe réplica na América do Sul**, então para um público só do Brasil ela não aproxima o dado (a mais perto continua nos EUA); desligar leva até 24 h para valer. Observável: `meta.served_by_region`/`served_by_primary` de cada consulta, que o `PERF_LOG` mostra em `d1[].r`/`p` (`p: false` = uma réplica respondeu). Docs: developers.cloudflare.com/d1/best-practices/read-replication/.
- `d1_databases` e `r2_buckets` ficam SEM `database_id`/`bucket_name` de propósito: o `/deploy` cria o D1 com `--location` antes do primeiro deploy e grava o `database_id`; o bucket o Wrangler cria no primeiro deploy (provisionamento automático, docs da Cloudflare). Sem `database_id` (botão Deploy, deploy direto), o banco nasce onde a Cloudflare escolher. Já tem banco? Acrescente `database_id`. Os scripts `db:migrate:*` usam o nome do binding (`DB`). No primeiro deploy manual, crie o banco com local (`wrangler d1 create`), grave o `database_id` e rode `npm run build && npx wrangler deploy` uma vez; depois `npm run deploy` (o `predeploy` migra antes de publicar). No botão Deploy (Workers Builds) o comando de deploy é `npx wrangler deploy && npx wrangler d1 migrations apply DB --remote` (migra depois porque o banco só existe depois do primeiro deploy).
- O estado local (D1, R2, DO) fica em `.wrangler/state/` (gitignorado e fora do watch do Vite).

### Riscos aceitos (de propósito)
- **Corrida no teto de 500 clientes**: `createClienteFn` conta e depois insere, sem transação; duas criações simultâneas da mesma pessoa podem passar de `CLIENTES_MAX` por uma ou duas linhas. Aceitável: o teto é para evitar excesso por engano, não uma cota de cobrança.
- **Segredo conferido só pelo tamanho**: `assertAuthSecret` exige 32 caracteres ou mais, mas não mede entropia (`'a'.repeat(32)` passa). Aceitável: quem gera com `openssl rand -base64 32`, como as instruções pedem, está coberto; a conferência existe para pegar segredo vazio ou esquecido.

### Proteções
- `PUBLIC_RATE_LIMIT` (5/min por IP) cobre os endpoints de login e as escritas públicas; `isRateLimited()` falha ABERTA sem o binding. Endpoint público de escrita novo? Aplique.
- `USER_RATE_LIMIT` (60/min por pessoa, chaves `user:<id>:leitura` e `user:<id>:escrita`, cada uma conta à parte) cobre as server functions de quem está logado; sem ele uma conta esgota a cota diária do D1 do plano gratuito. **Toda server function nova de quem está logado chama `await limitarUsuario(user.id, 'leitura' | 'escrita')` logo depois de checar a sessão** (`src/lib/rate-limit.ts`; lança erro em pt-BR, falha ABERTA sem o binding). `VITE_E2E_SEM_LIMITE` do Playwright desliga os dois limites. Troque o `namespace_id` 1002 por um número próprio do produto (como o 1001).
- Teto diário GLOBAL de e-mails de código (`src/lib/otp-daily-cap.ts`): o rate limit só aceita período de 10 ou 60 s, então o contador é uma linha por dia UTC em `otp_diario` (D1). Conta o envio de código e o cadastro com senha em `authRateLimit`, depois dos limites por IP e por e-mail; passou do teto, responde 429 como o limite normal. `OTP_DAILY_LIMIT` ajusta (padrão 100, a cota diária do Resend gratuito; `0` desliga); ajuste à cota do provedor de e-mail. Falha ABERTA se o D1 errar. O cron `otp.limpar-contador` apaga linhas com mais de 7 dias.
- `authRateLimit` lê o e-mail do corpo JSON ou `application/x-www-form-urlencoded` e responde 400 a corpo ilegível nos endpoints com e-mail (antes o limite por e-mail era pulado). Formato novo aceito pelo Better Auth? Acrescente em `readBody`.
- Cron (`src/lib/jobs.ts`): a ordem de `registerJob` é a ordem de execução. Expurgos (prazo legal) vêm primeiro; o lembrete de exclusão é o ÚLTIMO e tem teto (`REMINDER_BATCH`, 50 por noite, mais antigas primeiro), porque o plano gratuito limita as operações por invocação. Job novo de cortesia entra depois dos expurgos e com teto.
- **Cache imutável só nos arquivos com hash**: `public/_headers` dá `Cache-Control: public, max-age=31536000, immutable` a `/assets/*` (o Vite põe o hash no nome; conteúdo novo = nome novo). O HTML pré-renderizado e os arquivos sem hash de `public/` ficam com a revalidação padrão da camada de assets (`max-age=0, must-revalidate`) e a área logada e as server functions com `no-store` (`security-headers.ts`). O `/assets/` que não existe NÃO herda o cache (404 `no-store`, veja acima). Conferido por `e2e/security-headers.spec.ts` (contra o `npm run preview`) e `e2e/login.spec.ts` (`/app` logado: `no-store`). Não ponha `immutable` em regra mais larga que `/assets/*`.
- Cabeçalhos de segurança em `src/lib/security-headers.ts` (Worker) e `public/_headers` (assets/páginas estáticas): mantenha os dois iguais. Sem CSP de propósito (scripts inline do TanStack).
- Server functions recusam chamadas cross-site (`same-origin.ts`); use `method: 'POST'` em server function que muda estado. Rota de API que muda estado com o cookie do usuário chama `isCrossSiteRequest(request)` no começo (403), como `api/avatar.ts`.

| Contas vinculadas: tokens OAuth (`accessToken`, `refreshToken`, `idToken`; cifrados com `account.encryptOAuthTokens`, chave derivada do `BETTER_AUTH_SECRET`), hash da senha (se o login com senha estiver ligado) | `account` (D1) | Sem prazo próprio | Cascata ao apagar o usuário (fase 2). Nunca saem no "baixar meus dados" |
| Códigos de login (só o hash) e o e-mail no identificador | `verification` (D1) | 10 min de validade; o cron `auth.limpar-expirados` apaga os vencidos (a limpeza é diária) | Não há limpeza por usuário no encerramento: sai pelo cron, na primeira noite depois de vencer |
| Clientes cadastrados pela pessoa (nome, e-mail, situação) | `clientes` (D1) | Sem prazo próprio; teto de `CLIENTES_MAX` por pessoa | Cascata ao apagar o usuário (fase 2); entram no "baixar meus dados" |
| Trilha de auditoria: ação, e-mail do autor, IP e navegador | `audit_log` (D1), sem chave estrangeira de propósito | `AUDIT_RETENTION_DAYS` = 180 dias (job `auditoria.retencao`) | No expurgo da conta, `onBeforeAccountDelete('auditoria')` zera e-mail, IP e navegador das linhas dela; a linha (ação, data, id) fica até os 180 dias |
| Foto de perfil | R2, chave `avatars/<userId>` | Sem prazo próprio | `onBeforeAccountDelete('avatar')` apaga o objeto no expurgo. Não há "remover foto", só substituir |
| Cookies | Navegador | Sessão 7 dias; cache da sessão 60 s; `d1-bookmark` 1 h; checklist 1 ano | Expiram sozinhos; o encerramento limpa a sessão |

O "baixar meus dados" (`exportMyDataFn`) reúne conta, sessões, provedores, foto, auditoria (até 500 linhas) e clientes. Fica FORA do que o código apaga: logs do Worker na Cloudflare, backups do D1 (Time Travel) e e-mails já enviados pelo provedor; o prazo deles é o da Cloudflare e do provedor de e-mail, não do template.

### Encerramento de conta (duas fases)
- **Encerrar conta é em duas fases.** Fase 1 (`closeAccountFn`, botão "Encerrar conta"): roda os guards, marca `user.deletedAt`, apaga as sessões (num `db.batch`), audita `account.close_requested` e manda o e-mail `accountClosedEmail`. Nada é apagado. Fase 2 (cron `conta.apagar-encerradas`, depois de `ACCOUNT_RETENTION_DAYS` = 7 dias): guards de novo, `onBeforeAccountDelete`, apaga a linha de `user` (cascata em `session`/`account`; o delete reconfere `deletedAt`, então uma conta restaurada no meio do caminho não some) e audita `account.deleted` sem e-mail. No dia 5, `conta.lembrar-exclusao` manda `accountPurgeReminderEmail` uma vez (reivindicado por update condicional em `purgeRemindedAt`). A fase 1 é idempotente: o update condicional devolve `meta.changes`; com 0 linhas responde com o prazo do `deletedAt` já gravado, sem auditar nem mandar e-mail de novo.
- O `deleteUser` nativo do Better Auth fica DESLIGADO (`user.deleteUser.enabled: false`): ele apaga na hora e pularia o prazo. `deletedAt`/`purgeRemindedAt` são `additionalFields` com `input: false` (o cliente não escreve).
- Conta encerrada não entra: `databaseHooks.session.create.before` recusa com `ACCOUNT_CLOSED` (o formulário de código mostra a mensagem). Restaurar = `deleted_at = NULL` no D1 (é ação do suporte).
- Módulo novo com dado do usuário fora do D1 ou que deva sair no "baixar meus dados"? Registre em `src/lib/account-handlers.ts`: `onAccountDeletionGuard` (só confere; lance `AccountDeletionBlocked('mensagem em pt-BR')`), `onBeforeAccountDelete` (limpeza), `onAccountExport('chave', fn)` (nunca exporte token ou hash de senha). Os registros carregam pelo import em `src/server.ts`.

### Foto de perfil (R2)
- **Avatar tem limite**: PNG, JPEG ou WebP, até 2 MB (`AVATAR_MAX_BYTES`/`AVATAR_TYPES` em `src/lib/avatar.ts`). O tipo gravado vem dos primeiros bytes (`detectImageType`), não do que o navegador declarou.
- `POST /api/avatar`: same-origin → sessão (401) → `isRateLimited('avatar')` (429) → multipart com um campo `file` → grava em `env.BUCKET` na chave `avatars/<userId>` → `user.image = /api/avatar/<userId>?v=<timestamp>` → auditoria `account.avatar_set`. Não há "remover", só substituir.
- `GET /api/avatar/<userId>`: público. `Cache-Control: public, max-age=31536000, immutable` quando a URL leva `?v=` (muda a cada troca) e `public, max-age=300` sem ele; nos dois casos manda `ETag` e responde 304 com `If-None-Match`. Id inválido ou sem foto: 404.
- Cron diário (03:00 UTC) roda `runJobs` em `src/lib/jobs.ts`; jobs precisam ser idempotentes. Hoje: `auth.limpar-expirados`, `auditoria.retencao`, `conta.lembrar-exclusao`, `conta.apagar-encerradas` (no máximo 25 contas por noite) e `conta.apagar-social-nao-verificada` (usuário criado pelo login social com e-mail nunca verificado e mais de `UNVERIFIED_SOCIAL_DAYS` = 7 dias: mesmo caminho da fase 2, sem lembrete, auditado como `account.deleted` com `meta.reason`).

### Auditoria
- `audit({ action, actorId, actorEmail, targetType, targetId, meta, ...requestMeta(headers) })` em `src/lib/audit.ts`. **Sem sink registrado é no-op**: quem chama não precisa saber se a auditoria existe. O sink padrão (`src/lib/audit-d1.ts`, tabela `audit_log`) é registrado pelo import em `src/server.ts`; apagar aquela linha desliga a gravação.
- `action` é `<area>.<verbo>` em minúsculas (`auth.sign_in`, `auth.sign_out`, `auth.account_linked`, `account.created`, `account.name_changed`, `account.avatar_set`, `account.close_requested`, `account.deleted`); formato inválido é descartado com log.
- Nunca grave segredo (token, senha, código, cookie, chave) nem corpo de request. `formatAuditEntry` descarta chaves com cara de segredo em `meta` e só aceita valores primitivos, mas a regra é de quem chama.
- Com `waitUntil` à mão, passe-o (`audit(entry, { waitUntil })`, de `cloudflare:workers` ou do `ctx`) e a resposta não espera a gravação; sem ele, `await`. Falha de sink nunca derruba a ação.
- Evento novo do Better Auth? Acrescente no `auditAfterHook` (`src/lib/auth-audit-hook.ts`); ele só vê chamadas HTTP a `/api/auth/*`. Eventos que nascem dentro do Better Auth entram por `auditDatabaseHooks` (mesmo arquivo, ligado em `databaseHooks` no `auth.ts`): `auth.sign_out` (só o `POST /sign-out`), `auth.account_linked` (conta social ligada; `meta.provider`) e `account.created` (usuário novo, inclusive o do login social; `meta.method` traz o endpoint).

- Local Explorer (D1, R2, DO, logs e traces): http://localhost:3000/cdn-cgi/local/explorer (plugin v1 ≥ 1.50.0).

Para medir sem o cache da sessão, mande só o cookie `better-auth.session_token`; com ele, mande também `better-auth.session_data`. Código em `src/db/d1-trace.ts`, ligado em `src/server.ts` atrás de `import.meta.env.DEV` (some do build de produção). Só vê o pedido que recebeu o header: server functions chamadas pelo navegador não o levam.

### Arquivo antigo depois de um deploy
- **`/assets/<arquivo-que-não-existe>` responde 404 de verdade, nunca o HTML do app.** Cada build troca o hash dos arquivos e os antigos somem; uma aba aberta antes do deploy ainda os pede. Sem arquivo, o pedido caía no Worker e o TanStack devolvia a página de "não encontrado" (status 404, mas HTML): o navegador tentava rodar HTML como JavaScript e a tela quebrava sem pista. Agora `src/server.ts` barra no começo (`isAssetPath`, `src/lib/missing-asset.ts`): `404 text/plain`, `Cache-Control: no-store`, com os cabeçalhos de segurança. Rota que não é arquivo (`/nao-existe`) segue com a página própria.
- **O navegador recarrega UMA vez** quando um arquivo do app não carrega: `src/lib/chunk-reload.ts` ouve o `vite:preloadError` (o Vite o dispara na pré-carga de um chunk e num `import()` que falha), grava a hora em `sessionStorage` (`chunk-reload-at`) e chama `location.reload()`; de novo dentro de 60 s, não recarrega (sem laço; sem `sessionStorage` também não, pois sem a guarda não há como evitar o laço). Ligado em `getRouter` (`src/router.tsx`), só no navegador. O `lazyRouteComponent` do TanStack Router tem uma recarga própria para rota (guardada à parte): as duas são de uma vez só cada, nunca em laço. Teste: `e2e/deploy-antigo.spec.ts` (contra o `npm run preview`) e `chunk-reload.test.ts`/`missing-asset.test.ts`.

### Registro de desempenho (`PERF_LOG`)
- **Para medir no ar.** Variável `PERF_LOG=1` (em `.dev.vars` no dev; no Worker publicado, `npx wrangler secret put PERF_LOG` ou `wrangler.jsonc` > `"vars"` só durante a medição, ambos com o "sim" de quem pediu). Desligada (padrão), o servidor só compara uma string por pedido: nada é embrulhado e nenhuma linha sai. Ligada, `src/server.ts` escreve UMA linha JSON por pedido em `console.log` (`src/lib/perf-log.ts`), que aparece no `npx wrangler tail` e nos logs do painel:
  `{"perf":1,"method":"GET","path":"/app/clientes","status":200,"ms":412,"colo":"GIG","idas":3,"fila":2,"d1":[{"q":"select session","at":0,"ms":180},...]}`
- `ms`: do começo do pedido até o handler devolver a resposta (o corpo de uma página em streaming pode terminar depois; consultas feitas depois da resposta, como a auditoria em `waitUntil`, não entram). `colo`: onde o Worker rodou de fato (`request.cf.colo`); o cabeçalho de resposta `cf-placement` só existe depois que a resposta sai do Worker, pegue-o com `curl -sI`. `idas`: quantas idas ao D1. `fila`: a cadeia mais longa de idas uma depois da outra: `Promise.all` e `db.batch` contam como UMA, e cada nível custa uma viagem de rede até o banco. `d1[]`: tabela e verbo (`q`), início (`at`) e duração (`ms`) de cada ida, em ms desde o início do pedido; e, quando o resultado traz (`all`, `run` e `batch` trazem; `first`/`raw` não; no D1 local não existe), `r` (região do D1 que respondeu, `meta.served_by_region`, ex.: `ENAM`) e `p` (`true` se foi o primário, `false` se uma réplica); `d1_regioes` junta as regiões vistas. Só o caminho vai na linha, nunca a query string.
- Mesma contagem do rastreio de dev (`x-d1-trace`, abaixo), que continua valendo: os dois usam `src/db/d1-trace.ts`. Terminou de medir? Desligue (`wrangler secret delete PERF_LOG`, ou tire do `vars`). Não deixe ligado em produção: cada pedido gera uma linha de log (cota de logs do plano).
- Para um teste afirmar o limite de consultas em fila de uma rota, veja "Teste de consultas em fila" abaixo.

### Teste de consultas em fila
- **A meta vira teste.** Rota de leitura faz no máximo 2 consultas em fila ao D1 (`Promise.all` e `db.batch` contam como uma; veja `PERF_LOG` acima). No computador local o D1 responde em 1 ms e a fila não aparece, então o teste usa o D1 com atraso artificial: `medirFila(env.DB, () => minhaLeitura())` em `src/test/d1-fila.ts` roda a função com o banco lento e devolve `filaMax` (a cadeia mais longa), `total` e `consultas` (para a mensagem de erro). A conta é lógica, não em milissegundos: não oscila com a máquina.
- Molde: `src/lib/clientes-fila.test.ts` (a lista de clientes, com o Better Auth de verdade: sem o cache de cookie são 2 em fila, a sessão e a página; com o cache, 1). Para a função poder ser chamada direto, o miolo de servidor fica numa função comum (`src/lib/clientes-server.ts`) e a server function só a chama (`createServerFn(...).handler(() => listarClientes())`); `createServerFn` não roda fora do servidor do Start. Rota de leitura nova faz igual: miolo em `<area>-server.ts` e um teste que copia o molde. Contra-prova (feita ao criar o molde): uma leitura extra em fila na lista de clientes derrubou o teste (`3` > `2`); desfeita, voltou a passar.

### Decisões registradas
- **Teste de carga em staging (2026-11-11): o gargalo era a distância até o D1.** Worker no Rio, D1 primário na costa leste dos EUA (ENAM). 9.735 pedidos, 0% de erro. Causa: cada página logada faz várias consultas seguidas ao D1 e cada uma atravessa o continente.

  | Cenário | p95 |
  | --- | --- |
  | Estático (pré-renderizado) | 32 ms |
  | SSR público (`/login`) | 70 ms |
  | SSR logado (`/app`, `/app/clientes`) | 1.064 ms |
  | Escrita logada | 915 ms |

  Três correções: (1) Smart Placement (`wrangler.jsonc`); (2) cache da sessão em cookie por 60 s, com `disableCookieCache` nas ações sensíveis; (3) Sessions API do D1 por pedido + cookie `d1-bookmark`, pronta para a réplica de leitura (que se liga à mão no painel).

  Medido de novo no mesmo dia (tabela completa em `load/README.md`): com o Worker ao lado do banco, SSR logado caiu para 546 ms de p95 (mediana 294) e a escrita para 448 ms. O `mode: "smart"` não moveu o Worker no staging (`cf-placement: local-GIG`), porque o tráfego do teste saía todo do Rio; o ganho foi medido com `placement.region: "aws:us-east-1"` só no staging, e nessa configuração a página pública piorou de 70 para 235 ms, porque até ela ia aos EUA. Em 18/11 o template passou a vir com a região fixa (`aws:us-east-1`), porque tem banco (veja o item de Placement). Rodada 3, com Read Replication ligada (`read_replication.mode: auto`, via API da Cloudflare; o Wrangler não tem comando para isso) e as páginas logadas em 2 idas em fila ao D1 em vez de 5: SSR logado 385 ms de p95 (mediana 221) e escrita 419 ms. Todas as metas passaram.

  Idas em fila ao D1 por página, medidas com o rastreio acima (`/app` e `/app/clientes`, sem cache da sessão / com o cookie de cache): **antes 5 / 1, depois 2 / 1**. Antes, o guard e o loader liam a sessão cada um (2 consultas, `session` e `user`, em fila, duas vezes) e depois a consulta da página. Agora: a sessão é lida uma vez por pedido (`src/lib/request-session.ts`) e num JOIN só (`advanced.database.joins` + `sessionRelations` em `src/db/auth-schema.ts`), então sobram a sessão e a consulta da página. Com o cache do cookie válido, só a consulta da página. Não dá para tirar a última sem passar o `userId` pelo cliente (inseguro) ou fundir a sessão e a página numa consulta só.
- **i18n: só pt-BR.** Paraglide foi avaliado (referência ShipKit Lite) e deixado de fora: exige middleware no entry, reescrita de URL, thunks em toda string e dois globs por idioma, o que complica demais o template para quem está aprendendo. Textos ficam direto nos componentes e em `content/`. Se precisar de outro idioma, comece por `src/content/landing.ts` e `content/`.
- **Vitest puro, com stub de `cloudflare:workers`** (`src/test/cloudflare-workers.ts`); o comportamento real fica para o Playwright contra o `vite dev`. Com Wrangler de volta, `@cloudflare/vitest-pool-workers@0.23.0` passou a ser possível (testes dentro do workerd, com D1/R2/DO de verdade): é o próximo passo, fora do escopo da volta para v1.
- **Wrangler + plugin v1 em vez de `cf` + v2 (2026-11-07):** os dois seguem em beta e o template vai para leigos; o guia oficial do TanStack Start na Cloudflare usa plugin v1 + Wrangler. O estado v2 + `cf` está guardado na branch `cf-v2-beta`. Para voltar no GA: confirmar com `npm view cf dist-tags` e `npm view @cloudflare/vite-plugin dist-tags` que não há mais `beta`, ler os changelogs e, numa branch nova, rodar `npx cf migrate --bundler vite` (lê o `wrangler.jsonc`). Conferir à mão o que ele não converte: o Durable Object (`exports.durableObject({ storage: 'sqlite' })`), o id do D1 e os `--dir drizzle` dos scripts de migração; comparar com `git diff main cf-v2-beta`.
- **Devtools do TanStack** só em dev (`src/components/devtools.tsx`, carregado atrás de `import.meta.env.DEV`) e só no navegador (`<ClientOnly>`).
- **O `npm run dev` travava com o primeiro pedido abandonado (2026-11-10).** Causa: o `lazy()` do Devtools era renderizado no servidor (veja "React.lazy só no cliente" nas Regras). Aparecia com qualquer ferramenta que confere o servidor com `HEAD /` usando User-Agent de navegador (o painel de preview do Claude faz isso a cada 2 s) ou com uma aba fechada no meio da primeira carga. Com User-Agent de robô (`curl`) não aparecia, porque aí o TanStack espera a página inteira antes de responder. Produção nunca foi afetada: lá o `Devtools` é `() => null`.
- `env.COUNTER` já vem tipado como `DurableObjectNamespace<Counter>` pelo `wrangler types`: sem cast.
